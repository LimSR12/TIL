# N+1 문제 완전 정복

---

## 1단계 — 문제 이해

### N+1이란?

1번의 쿼리로 N개의 데이터를 가져온 뒤, 각 데이터의 연관 엔티티를 조회하기 위해 **N번의 추가 쿼리**가 발생하는 문제다.

```
posts 10개 조회        → SELECT * FROM posts (1번)
post[0].getCategory()  → SELECT * FROM categories WHERE id=? (1번)
post[1].getCategory()  → SELECT * FROM categories WHERE id=? (1번)
...
post[9].getCategory()  → SELECT * FROM categories WHERE id=? (1번)

= 총 1 + 10 = 11번 쿼리
```

### 왜 발생하는가?

JPA의 연관관계 기본 fetch 전략이 **LAZY 로딩**이기 때문이다.

```java
@ManyToOne(fetch = FetchType.LAZY)
private Category category;
```

LAZY 로딩은 연관 엔티티를 **실제로 접근하는 시점**에 쿼리를 날린다.
반복문 안에서 연관 엔티티에 접근하면 반복 횟수만큼 쿼리가 발생한다.

```java
// 이 코드가 N+1을 유발
posts.forEach(post -> post.getCategory().getName()); // 각 post마다 SELECT 발생
```

### EAGER로 바꾸면 해결되나?

```java
@ManyToOne(fetch = FetchType.EAGER) // ❌ 해결 안 됨
private Category category;
```

EAGER는 Post를 조회할 때마다 Category를 **무조건** 함께 조회한다.
필요 없는 상황에서도 항상 쿼리가 발생하므로 오히려 더 나쁘다.
**항상 LAZY를 기본으로 설정하고, 필요한 경우에만 fetch join으로 해결한다.**

### 로그로 확인하는 방법

```yaml
# application.yml
spring:
  jpa:
    show-sql: true
    properties:
      hibernate:
        format_sql: true

logging:
  level:
    org.hibernate.SQL: DEBUG
    org.hibernate.orm.jdbc.bind: TRACE # 바인딩 파라미터 확인
```

## 2단계 — 해결 방법

### 방법 1. fetch join

JPQL에서 `JOIN FETCH`를 사용해 연관 엔티티를 **한 번의 쿼리로 함께 조회**한다.

```java
@Query("""
    SELECT p FROM Post p
    LEFT JOIN FETCH p.category
    WHERE p.status = :status
    AND p.deletedAt IS NULL
""")
List<Post> findAllWithCategory(@Param("status") PostStatus status);
```

```sql
-- 실행되는 쿼리 (1번)
SELECT p.*, c.*
FROM posts p
LEFT JOIN categories c ON p.category_id = c.id
WHERE p.status = ?
```

### 방법 2. @EntityGraph

어노테이션으로 fetch join을 선언하는 방식이다.
`@Query`를 작성하지 않아도 되므로 간단한 경우에 유용하다.

```java
@EntityGraph(attributePaths = {"category", "tags"})
List<Post> findByStatus(PostStatus status);
```

### fetch join vs @EntityGraph 비교

|             | fetch join            | @EntityGraph |
| ----------- | --------------------- | ------------ |
| 선언 방식   | JPQL 직접 작성        | 어노테이션   |
| 복잡한 조건 | ✅ 자유롭게 작성 가능 | ❌ 제한적    |
| 가독성      | 쿼리가 길어질 수 있음 | 간결함       |
| 컬렉션 조회 | DISTINCT 필요         | 자동 처리    |
| 주 사용처   | 복잡한 쿼리           | 단순 조회    |

## 3단계 — 페이징 + fetch join의 함정

### 문제 상황

컬렉션(OneToMany, ManyToMany)을 fetch join하면서 페이징을 함께 쓰면 경고가 발생한다.

```
WARN: HHH90003004 - firstResult/maxResults specified with collection fetch;
applying in memory
```

**DB에서 LIMIT을 적용하지 못하고 전체 데이터를 메모리에 올린 뒤 페이징 처리한다.**
데이터가 많아지면 OOM(OutOfMemoryError)으로 이어질 수 있다.

### 왜 발생하는가?

```
posts 3개, 각 post에 tags 4개씩 있다고 가정

fetch join 결과 (DB 레벨)
| post_id | tag_id |
|---------|--------|
|    1    |   A    |
|    1    |   B    |
|    1    |   C    |
|    1    |   D    |
|    2    |   A    |
...

LIMIT 3을 DB에서 적용하면?
→ post 1의 tag 3개만 잘려서 나옴 (데이터 오염)
→ Hibernate가 이를 알기 때문에 메모리에서 페이징 처리
```

### 해결 방법 — BatchSize

fetch join 대신 **BatchSize**를 사용한다.
연관 엔티티를 개별 조회하되, **IN 절로 묶어서 한 번에** 가져온다.

```java
// 방법 1. 엔티티에 직접 설정
@BatchSize(size = 100)
@OneToMany(mappedBy = "post")
private Set<Tag> tags;
```

```yaml
# 방법 2. application.yml 전역 설정 (권장)
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

```sql
-- BatchSize 적용 후 실행되는 쿼리
SELECT * FROM posts WHERE ... LIMIT 10          -- 1번
SELECT * FROM tags WHERE post_id IN (1,2,3...)  -- 1번 (IN절로 묶음)
SELECT * FROM categories WHERE id IN (1,2,3...) -- 1번

= 총 3번 (N+1 해결)
```

### @BatchSize vs default_batch_fetch_size

|           | @BatchSize                  | default_batch_fetch_size |
| --------- | --------------------------- | ------------------------ |
| 적용 범위 | 특정 컬렉션/엔티티          | 전역 (모든 LAZY 로딩)    |
| 설정 위치 | 엔티티 클래스               | application.yml          |
| 유연성    | 컬렉션마다 다르게 설정 가능 | 일괄 적용                |
| 권장 여부 | 부분 적용 시                | **일반적으로 권장**      |

## 4단계 — 실무 관점

### N+1을 항상 없애야 하나?

**항상 그런 것은 아니다.** 상황에 따라 트레이드오프를 고려해야 한다.

```
fetch join 사용 시
장점: 쿼리 횟수 감소
단점: 쿼리 복잡도 증가, 불필요한 데이터도 JOIN해서 가져옴

N+1 허용 시
장점: 쿼리 단순, 필요할 때만 조회
단점: 쿼리 횟수 증가
```

### 판단 기준

| 상황                              | 권장                      |
| --------------------------------- | ------------------------- |
| 목록 조회 (대량 데이터)           | fetch join 또는 BatchSize |
| 단건 상세 조회                    | fetch join                |
| 연관 엔티티 접근 빈도가 낮은 경우 | LAZY 그대로 허용          |
| 실시간 트래픽이 많은 API          | 반드시 N+1 제거           |

## 면접 단골 질문 & 모범 답변

**Q. N+1 문제가 무엇인지 설명해주세요.**

> 1번의 쿼리로 N개의 데이터를 조회한 후, 각 데이터의 연관 엔티티를 접근할 때 N번의 추가 쿼리가 발생하는 문제입니다. JPA의 LAZY 로딩 전략에서 연관 엔티티를 반복 접근할 때 주로 발생합니다.

**Q. N+1을 해결하는 방법을 아는 대로 말해주세요.**

> fetch join, @EntityGraph, BatchSize 세 가지 방법이 있습니다. fetch join은 JPQL로 직접 JOIN FETCH를 작성해 한 번의 쿼리로 가져오고, @EntityGraph는 어노테이션으로 간단히 선언합니다. BatchSize는 IN절로 묶어서 쿼리 횟수를 줄입니다.

**Q. fetch join과 EntityGraph의 차이는?**

> 둘 다 즉시 로딩으로 연관 엔티티를 가져오지만, fetch join은 JPQL을 직접 작성해 복잡한 조건을 자유롭게 표현할 수 있고, @EntityGraph는 어노테이션으로 선언해 간결하지만 복잡한 쿼리에는 한계가 있습니다.

**Q. 페이징과 fetch join을 같이 쓰면 어떤 문제가 생기나요?**

> 컬렉션을 fetch join하면서 페이징을 함께 사용하면 DB에서 LIMIT을 적용하지 못하고 전체 데이터를 메모리에 올린 뒤 페이징 처리합니다. 데이터가 많아지면 OOM이 발생할 수 있고, Hibernate는 `HHH90003004` 경고를 남깁니다. 이 경우 fetch join 대신 BatchSize를 사용해 해결합니다.
